# Lecture Builder 3.2

Многоагентная подготовка русскоязычных вузовских лекций для Antigravity, Codex и совместимого режима Gemini. Канонические правила находятся в `.agents/`; Python-инструменты проверяют артефакты, происхождение доказательств, нумерацию и DOCX.

## Что изменилось в 3.2

Проверка страниц больше не доверяет числу страниц или `verified_pages`. Ссылка связана с соседним claim-маркером и напечатанной меткой страницы. Строгая проверка сопоставляет исходный файл, его хеш, сохранённый UTF-8 текст, точный срез и `fragment_id`.

Финальные рецензии содержат обязательные проверки, идентификаторы независимых контекстов, хеши реально проверенных артефактов и охват тезисов. Пустой `pass`, устаревшее одобрение и исправление без независимой перепроверки не дают допуск. Нумерация теперь завершается **до финальных рецензий и fact check**, чтобы все они относились к одному неизменяемому тексту.

Добавлены исполняемый граф этапов, проверка объявленных выходов, инвалидирование зависимостей, ограниченный цикл адресных исправлений и построение контекстного пакета раздела. Обновлены 17 Skills; Gemini получает отдельные научный, педагогический и fact-check профили.

## Быстрый старт

```bash
python -m pip install -e '.[dev]'
python scripts/validate_pipeline.py --mode source
pytest
```

Заполните `input/lecture_config.md` по `input/lecture_config.example.md`. Укажите аудиторию, вопросы, компетенции, источники и ограничения. `input/` принадлежит пользователю; все результаты создаются в `output/`.

В Antigravity используйте `/build-lecture`; в Codex поручите `lecture_orchestrator` выполнить `.agents/workflows/build-lecture.md`. Gemini compatibility читает те же канонические правила. Наличие профиля не доказывает доступность конкретного инструмента: недоступную возможность нужно явно сообщить.

## Процесс

```text
config → поиск по пробелам → извлечение → bibliography + evidence
→ blueprint + задания → авторы разделов → проверка структуры
→ методические вставки / визуальные планы → графики → сборка
→ независимые черновые рецензии ↔ адресные исправления
→ lecture_edited.md → нумерация → lecture_final.md
→ независимые финальные научная и педагогическая проверки
→ fact check → DOCX → строгий допуск
```

Планы рисунков хранятся в `output/plans/`; renderer работает с их копиями в `output/`. Черновые рецензии сохраняются в `output/reviews/draft/`; итоговые — в `output/reviews/`. Это предотвращает перезапись уже зафиксированных выходов предыдущих этапов.

```bash
python scripts/manifest.py next
python scripts/repair_plan.py --phase draft --cycle 1
python scripts/number_formulas.py output/lecture_edited.md \
  -o output/lecture_final.md --registry output/formula_registry.json
# Затем: финальные независимые рецензии и fact check.
bash scripts/md2docx/run_md2docx.sh output/lecture_final.md \
  -o output/lecture_final.docx
python scripts/validate_pipeline.py --mode artifacts --strict \
  --report output/quality_report.json
```

`repair_plan` не исполняет LLM автоматически: он формирует проверяемые задания для оркестратора выбранной платформы. План `blocked` запрещено dispatch-ить. `max_review_cycles` ограничивает цикл. Полный граф, владельцы исправлений и обязательные выходы определены в `lecture_tools/stage_graph.py`.

## Нумерация и учебные материалы

Для лекции 17 вопросы имеют номера 17.1, 17.2; подразделы — 17.1.1; формулы — (17.1), рисунки — Рисунок 17.1, таблицы — Таблица 17.1. Счётчики независимы и сквозные. Технические имена файлов сохраняют локальные номера `section_1_...`.

Лекция включает объяснение механизма, определения, обозначения и единицы, допущения, пример, типичные ошибки, микро-выводы и переходы. Методические вставки ограничены конфигурацией. Графики строятся детерминированно по данным; схемы явно помечаются как условные. Промпты изображений остаются в `output/image_prompts.md`.

## Миграция и границы проверки

Старые evidence без `fragment_id`, исходных файлов/текста и координат нужно пересоздать из реально доступных источников. Старые рецензии и manifest без объявленных `inputs` не следует искусственно дополнять статусами успешной проверки. Обновлённые скиллы/схемы/код участвуют в content hash; отдельного трекинга моделей и промптов нет.

Структурный score не измеряет научную правильность или учебную эффективность. Сверка хешей не доказывает семантическую поддержку тезиса; её проверяют независимые рецензенты. Проект не воспроизводит научные эксперименты. DOCX-проверки не заменяют визуальную проверку макета.
